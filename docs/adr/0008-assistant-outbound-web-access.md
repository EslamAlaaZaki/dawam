# The assistant reaches the web only through DAWAM's own tools, off by default

The assistant gets two tools, `web_search` and `web_fetch`, implemented in DAWAM (the `web` module), not as provider-native server tools: they then work with every model adapter and go through our audit, data-sharing and internal-only checks. Both are off by default. An admin turns them on with one switch on the admin page (stored in the database like LLM providers, not in `.env`) and registers the search providers there.

**Providers.** Search sits behind a `SearchProvider` port with two adapters for now, both free: **SearXNG** (self-hosted, internal; the admin enters its URL and enables JSON output in its `settings.yml`; DAWAM calls `GET <url>/search?q=…&format=json`) and **LangSearch** (a cloud API, external; the admin enters an API key, sealed with `SecretBox` like LLM provider keys; DAWAM calls `POST https://api.langsearch.com/v1/web-search` with a Bearer key). Both can be registered and tested at once. The admin picks the provider of normal Workspaces (any registered one) and the provider of internal-only Workspaces (internal ones only). The Workspace's existing `internal_only` flag decides which applies. An internal-only Workspace never uses an external provider: the API refuses the choice, and the lookup checks the provider's kind again before every call. **Failover (#540).** SearXNG asks public engines that can block it (rate limits, CAPTCHAs), so a search that fails is tried once on one other registered provider, in either direction. Failure means: cannot be reached, timeout, an HTTP error (429 included), an unusable reply, or no results while SearXNG reports unresponsive engines (blocked or rate limited). Results from any engine are never a failure, and an empty result with no unresponsive engine is a normal empty result. There is no setting: registering a second provider is the admin's opt-in. The check on the provider's kind is repeated right before the failover call, so an internal-only Workspace never reaches an external provider and, with no other internal one, gets the error. Each attempt is audited before its call; the result names the provider that answered, and when both fail the tool returns one `web_search_failed` error ("unavailable right now"). A failover is one `web_search` call, counted once. Others (Brave, Tavily) can be added later as more adapters.

**When the tools are offered.** `web_search` is offered when the switch is on and the Workspace's kind has a registered provider; otherwise it is not in the tool list at all. `web_fetch` shares the switch; an internal-only Workspace gets it only once the admin has given internal-only Workspaces a provider, which is the admin's opt-in to web access for them. Both are chat-only (a background job never reaches the web) and need only `ask_assistant`; every call still runs as the member through `BoundTools.execute`.

**Queries.** The model's query loses its values before it leaves: quoted literals, tokens with more than five digits (ids, accounts), amounts, dates, and everything the PII validators recognise (emails, phones, IBANs, ID and card numbers, and names when NER is on). Short numbers stay ("IFRS 9", "SQL Server 2019"). The query as sent is audited (`web_search`, channel `ai`) before the call, kept on the run and shown in the chat under the answer.

**Fetch.** DAWAM fetches the page itself first (the fallback below reads what it can't). Only `http`/`https` on ports 80 and 443, no credentials in the URL. The host is resolved and every address must be public: private, loopback, link-local (cloud metadata), shared, reserved and multicast ranges are refused, as are IPv6 addresses embedding one (IPv4-mapped, NAT64, 6to4, Teredo). The connection goes to a checked address (TLS still verified against the host name), so a second DNS answer cannot redirect it (rebinding). A host with several addresses is resolved once per hop, and when the connection to one fails or times out the next is tried, at most three addresses and 20 seconds per hop (#538); any HTTP reply, a 403 included, is the site's answer and ends the attempts. The 10-second cap applies to each attempt. Redirects are followed by hand, at most five, each checked the same way. The body is capped at 2 MB and 10 seconds, only text types are read, HTML is reduced to text, and the model sees at most 12,000 characters. Each fetch is audited (`web_fetch`).

`web_fetch` reads only a URL the member wrote in the conversation or one a `web_search` returned in the same answer. A URL the model composed could carry Workspace data out in its path or query string, steered by a prompt injection; limiting fetches to URLs the model did not write closes that channel.

**Reader fallback (#537).** Bot protection refuses many sites to DAWAM's own fetch, so a page it cannot read goes to **Jina Reader** (`GET https://r.jina.ai/<url>`), an external service. It is on by default with no admin setting, a deliberate exception to "nothing external unless the admin registers it": the web access switch (off by default) still gates it, and it never runs for an internal-only Workspace (checked again, with the switch, right before every call). It works without a key; the optional `DAWAM_JINA_API_KEY` is deployment configuration in the environment, because there is no admin setting to hold it, and it is only ever sent to Jina.

It runs only after the URL passed the URL and public-address checks, and only when the page answered with HTTP 4xx or 5xx, the request timed out or the connection failed after the host resolved, or the page was read but is empty or thin (#547: an HTML page with under 1,500 characters of text once cleaned; `text/plain`, JSON, CSV and XML are never thin). DAWAM's own HTML reduction also skips the contents of `nav`, `footer`, `aside` and a page-level `header` (a `header` inside an `article`, `section` or `main` is kept, and furniture left open does not drop the rest of the page; the parser tracks at most 500 open tags, so a hostile page costs linear time), so menus no longer use up the 12,000 characters. For an empty or thin page the longer text wins: Jina's replaces DAWAM's only when it is longer and, for a thin page, its title and first 600 characters hold no block-page phrase (`BLOCK_PHRASES` in `fetch.py`: "access denied", "just a moment", "captcha" and the like), and when the read fails or is not longer the member gets DAWAM's own text as an ok result (an empty page with no better read stays the `empty_page` failure). It never runs for a blocked address (on a redirect hop too), an invalid URL, a host that did not resolve (the address could not be checked, and an internal name must not leave the network), an unsupported type, or a URL the model composed. A **URL with a query string never goes to Jina**, because even a member-pasted URL can carry a token or data; the fragment is removed. What goes is the URL the member or the search gave, not a redirect's target.

Jina answers HTTP 200 even when the site refused it, so a `Warning:` line above the text or no text at all is a failed read, like a Jina HTTP error or timeout. A failed read is not retried, and the tool returns DAWAM's own error. The attempt is audited before the call as another `web_fetch` entry with `"reader": "jina"`, the chat shows "Read a web page (Jina)", and the text is a tool result like any other page.

**Browser fallback (#545).** Between DAWAM's own fetch and Jina sits **Crawl4AI**, a full browser inside the installation, optional and off unless the operator starts the `crawl4ai` Compose profile and sets `DAWAM_CRAWL4AI_URL`. There is no admin setting. The chain is own fetch → Crawl4AI → Jina → the tool's failure reply for a normal Workspace, and own fetch → Crawl4AI for an internal-only one; each step runs only if the one before it gave no usable page, and a read that is used stops the chain. Its triggers and refusals are Jina's: after an HTTP 4xx or 5xx, a timeout or failed connection after the host resolved, or an empty or thin page (the longer text wins, and if every step fails DAWAM keeps its own text); never for `address_blocked`, `invalid_url`, `url_not_given`, an unresolved host or an unsupported type. Unlike Jina, it may have **a URL with a query string**, because it stays on this network and the target would get that URL from DAWAM's own fetch anyway, and **internal-only Workspaces can use it**. The switch is read again right before the call. The fragment is removed, and the URL the member or the search gave goes, not a redirect's target. The attempt is audited before the call as a `web_fetch` entry with `"reader": "crawl4ai"`, the chat shows "Read a web page (Crawl4AI)", and the text is a tool result like any other page.

**Time limit (#545).** One `web_fetch` spends at most 45 seconds across all steps. Each step's timeout is the smaller of its own (own fetch as above, Crawl4AI 25 s, Jina 30 s) and the time left, and a reader with under 5 seconds left is skipped and not audited. A timeout now bounds a whole HTTP exchange, not each read of it.

**A read through Crawl4AI.** `POST <DAWAM_CRAWL4AI_URL>/crawl` through the `Network` port, with the optional `DAWAM_CRAWL4AI_API_TOKEN` as a Bearer token. The service's address is operator configuration, so the public-address check does not apply to it; the target URL has passed every check before it gets here. Every request sends `wait_until: domcontentloaded`, `page_timeout: 20000`, `delay_before_return_html: 4.0`, `excluded_tags` (`nav`, `header`, `footer`, `aside`, `form`, `script`, `style`, `noscript`, `iframe`) and a `DefaultMarkdownGenerator` with `ignore_links` and `ignore_images`, and DAWAM uses the raw Markdown. `PruningContentFilter` is not used: it removed only another 1–9% in the measurement, and a filter like that can remove real text. Crawl4AI reported success for a 403, a 401 and a CAPTCHA page, so a read fails when the reply reports failure, the target's status is 400 or higher, the text is empty, or the title or first 600 characters hold a `BLOCK_PHRASES` phrase. A reply over 2 MB, a service that cannot be reached, and a timeout are failed reads too, and none is retried.

**Locked-down network (#545).** A browser runs the page's JavaScript and loads whatever the page asks for, so DAWAM's public-address check does not cover its requests. A hostile page must not be able to reach anything internal:

- `crawl4ai` is on `crawl4ai-internal` only, an `internal: true` network shared with `app`, the filter and a resolver. It is not on the default network, so it cannot reach the database, SearXNG, Ollama or Mailpit. It has no host port and a 2 GB memory limit, runs at most 2 pages at once (`crawler.pool.max_pages`), with no capabilities and a read-only root file system. Only `app` joins that network; `worker` does not, because web fetch runs in chat only.
- Its only way out is its browser's proxy setting. Crawl4AI 0.9.5 always points the browser at its own proxy on loopback and refuses a request that sets another (the by-hand check asks for loopback addresses too). That proxy resolves each host once, refuses any non-global answer, and asks the upstream it was given (`CRAWL4AI_UPSTREAM_PROXY`) for the IP address it checked. The upstream is `egress-filter`, on the internal network and on `crawl4ai-egress`, the only way off it.
- **`egress-filter` is Squid (`ubuntu/squid`), and it trusts nothing above it.** It refuses private, loopback, link-local, shared, reserved and multicast destinations, in IPv6 too, including the ranges that embed an IPv4 address. `dst` checks the address, whatever name it came under, and refuses a host if any of its addresses is listed. A redirect is a new request to the proxy, so it is checked too. A compromised browser could ask it for a host name directly, so `negative_dns_ttl` keeps every DNS answer for 5 minutes, and the check and the connection use the same one (rebinding). It reaches ports 80 and 443 only, and serves that network only.
- Crawl4AI must resolve a host itself, and Docker's resolver answers no outside name on an internal network. So `crawl4ai-dns` (CoreDNS) answers for it, through a mounted `resolv.conf`. It is on the same two networks and not on the default one, so DAWAM's services do not resolve through it. A hostile page gains nothing from it: it can already name any public host.

The design follows the source of the pinned Crawl4AI version and the filter's documentation. CI never starts it: `tests/web/test_crawl4ai_compose.py` reads both Compose files and the filter's settings, and whether a running network holds is the by-hand check in `deploy/README.md`, "Crawl4AI", recorded in the PR.

**Version and token.** The ticket measured 0.7.4, but versions before 0.9.5 have published critical and high advisories on the server (hooks and `extra_args` RCE, `file://` reads, proxy and SSRF bypasses, TLS verification off), so the image is pinned to 0.9.5 by digest. That server binds beyond loopback only with a token, so `DAWAM_CRAWL4AI_API_TOKEN` exists next to the URL; both Compose files hand the same variable to the server, and without it the server stays on its own loopback and the step fails as a failed read.

**Identity (maintainer decision, 1 November 2026).** Crawl4AI runs the full browser with its default identity. `light_mode`, `text_mode` and `AsyncHTTPCrawlerStrategy` are not used: light mode made no measurable difference to full mode, and HTTP mode failed on Wikipedia and cannot read JavaScript pages. `magic`, `enable_stealth`, `simulate_user`, `override_navigator`, external proxies and CAPTCHA solving are not enabled. Those defaults present a normal Chrome browser and hide the automation flag, which may be why it reads pages that refuse a plain headless browser. The admin who enables the profile is told to check the rules of the sites involved (`deploy/README.md`).

**Untrusted content.** Results and pages are tool results, so they are quoted as data and pass through the prompt-injection check like every other tool result; a flagged page is marked in the chat.

## Considered options

- **Provider-native web search** (Anthropic, OpenAI, Gemini grounding): rejected; it runs at the provider outside our gateway, audit and internal-only checks, and does not exist for self-hosted models.
- **Configure providers in `.env`**: rejected by the maintainer; an admin must be able to register, test and switch providers in the app, like LLM providers. Jina's optional key is the one exception: the fallback has no admin setting, by the maintainer's decision.
- **Brave, Tavily, Bing, Google**: not now. Brave has no free tier, Tavily only one-off credits, Bing's Search APIs are retired and Google's Custom Search JSON API closes on 1 January 2027.
- **Let `web_fetch` read any public URL**: rejected; the SSRF guard stops internal addresses but not data leaving in a URL the model wrote.
- **A plain headless browser for refused pages**: rejected; on 13 refused pages plain headless Chromium read 3, Jina Reader 10 and Crawl4AI with default settings 11 (#545). Crawl4AI also stays on this network, so it serves internal-only Workspaces and URLs with a query string, which is why it was added with the network above. Stealth and CAPTCHA solving are out.
- **Pointing the browser straight at the filter**: not possible on 0.9.5, which always routes the browser through its own proxy and refuses a proxy in the request. A filter without a resolver is not possible either: that proxy resolves every host itself.
- **Another filter**: Smokescreen resolves and pins by design, but would have to be built here rather than pinned as a published image; Envoy needs far more configuration for the same refusals. Squid is packaged by Ubuntu, supported on 26.04 until May 2031.
- **Crawl4AI 0.7.4, as measured**: rejected for the advisories above.
- **A switch or admin setting for the fallback**: rejected by the maintainer; the web access switch and the internal-only exclusion are the controls.
- **An allow-list of domains for fetch**: not now; it needs upkeep by the admin, and the public-address check plus the "member's or search result's URL" rule cover the risks the ticket names.
